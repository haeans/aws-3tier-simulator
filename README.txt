==============================================================
 AWS 3-Tier 아키텍처 시뮬레이터
==============================================================

캔버스 위에 AWS 서비스 박스와 영역(VPC/AZ/서브넷)을 배치하고 연결해서,
3-Tier 아키텍처가 논리적으로 성립하는지 검증해 보는 학습용 웹 도구.
실제 AWS 리소스는 만들지 않는다.

- 최종 목표: IDC(온프레미스)에서 AWS로, 서버에서 서버리스·컨테이너로 옮기는 마이그레이션 과정을
  CI/CD와 함께 설계해 보고, 그 구성의 성능(트래픽 부하·장애·요청)까지 시뮬레이션으로 확인하는 도구
  (2026-10-15 사용자 결정. 진행 순서는 7장 [작업 계획 3차])

- 대상: 개발자 본인(학습/재미), AWS를 처음 접하는 사람
- 형태: HTML + CSS + JavaScript 파일 (외부 라이브러리 없음, 서버 없이 실행)
- 환경: 데스크톱 브라우저 (Edge / Chrome 권장)


--------------------------------------------------------------
 1. 실행 방법
--------------------------------------------------------------
index.html 파일을 브라우저로 열면 된다. (서버 불필요, 더블클릭으로 실행)
css/, js/ 폴더가 index.html과 같은 위치에 있어야 한다. 공유할 때는 폴더째 전달한다.

작업 내용은 브라우저 저장소(localStorage)에 자동 저장되므로,
같은 브라우저로 다시 열면 이어서 작업할 수 있다.
다른 브라우저나 시크릿 창에서는 빈 캔버스로 열린다.


--------------------------------------------------------------
 2. 주요 기능
--------------------------------------------------------------
[배치]
- 좌측 팔레트에서 영역/서비스를 끌어다 격자 캔버스에 배치 (격자 스냅)
- 영역 중첩 규칙: VPC > AZ > 서브넷(퍼블릭/프라이빗/DB) > 서비스
- Auto Scaling 그룹 영역: 여러 AZ의 프라이빗 서브넷에 걸쳐 놓고 EC2를 감싸는 점선 영역
- 서비스별 배치 가능 위치 제한 (어기면 안내 메시지와 함께 되돌림)
- 서비스 박스끼리, 같은 단계 영역끼리 겹침 방지
- IGW / VPC Endpoints / Client VPN은 VPC 경계선에 자동으로 붙음
- 영역 크기 조절 (좌상단·우하단 손잡이), 영역 이동 시 안의 항목도 함께 이동
- 여러 개 선택: Shift+클릭(넣고 빼기), Shift+드래그(범위 선택, 영역 위에서도 가능) → 함께 이동·Delete로 함께 삭제
  (서비스 박스만 여러 개 선택 가능)
- [기본 틀 불러오기]: VPC 1 + AZ 2 + AZ별 퍼블릭/프라이빗/DB 서브넷

[연결]
- [연결 모드]에서 박스 → 박스 클릭으로 양방향 직각 화살표 연결
- 연결점(변 중앙) 직접 선택, 끝점 손잡이로 연결 변 변경, 가운데 손잡이로 경로 이동
- 자동 경로는 다른 박스를 피해서 그림. 선에 마우스를 올리면 그 선만 강조
- 선끼리 겹치면 간격을 벌려 그림 (한 변의 여러 선은 연결점을 나눔)

[검증]
- [검증하기]: 정상 / 경고 / 오류 3단계 판정 + 문제 박스 강조 (규칙 7개)
- 검증 중에는 버튼이 [검증 종료]로 바뀜. 누르면 결과를 지우고 검증 전 화면으로 (구성은 그대로)
- 개선·제거 제안 (판정과 별개, 규칙 10개)
- 잘한 점: 좋은 구성이 실제로 있으면 근거 태그와 함께 칭찬 (판정 5개·제안 7개 규칙에 짝지음). 문제 다음, 제안 앞에 표시
- 판정·제안마다 Well-Architected 기준 태그와 "왜 그런지" 근거, 근거 문서 링크(자세히) 표시
- 서비스 설명·연결 안내는 AWS 공식 문서 기준 (설명 패널에서 공식 문서 열기)
- 검증 후 요청 방향 화살표 + 사용자부터 한 구간씩 차례로 흐르는 점 (초록=정상, 노랑=병목, 빨강=오류)
  Route 53(주소 묻기)은 왕복, WAF(요청 검사)는 박스 반짝임으로 표시

[성능 시뮬레이션]  (만드는 중, 12-3까지)
- 결과 영역의 [성능 시뮬레이션] 탭: 기본 트래픽(초당 요청 수) 슬라이더로 요청을 흘려봄
- 시간 흐름: 재생·멈춤·배속(1x/5x/10x), 경과 시간
- 시나리오: 평소(일정), 급증(60초마다 15~35초에 3배), EC2 장애(10초 고장·100초 복구), AZ 장애·DB 장애(10초 고장·130초 복구)
- 최근 5분 응답 시간·성공률 그래프 (급증 구간은 붉은 배경, 사건은 세로 점선)
- 장애 넣기: [⚡ 장애 넣기]를 켜고 EC2·RDS 박스나 AZ 영역을 누르면 고장/복구, [모두 복구]
  자동 복구: LB 상태 확인(30초마다, 2번 실패 → 제외, 5번 성공 → 복귀), RDS Multi-AZ 장애 조치(약 90초 동안 DB 요청 실패)
  멈춘 박스는 회색 + ✕, 박스 안에 진행 상황(확인 1/2, 조치 25초, 복귀 확인 2/5), 패널에 사건 기록
- 처리량·성공률·평균 응답 시간, 병목·연결 끊김 안내
- 캔버스: EC2·RDS 박스 색이 사용률별로 바뀜 (초록 / 노랑 80%↑ / 빨강 100%↑ 깜빡임), 박스 안 사용률 막대와 실패 수
  요청이 지나가는 선마다 초록 점이 흐름 (많을수록 촘촘). 실패하는 몫의 점은 도착 직전 빨갛게 변해 사라짐
  RDS와 연결되지 않은 EC2는 빨간 점선 테두리 + "연결 끊김"
- 숫자는 학습용 가정값 (EC2 1대 초당 100요청, RDS 초당 300요청). LB·IGW·CloudFront는 제한 없음

[기타]
- 줌 60~150% (버튼 / Ctrl+휠), 자동 저장 (배치·줌·스크롤 위치)
- 되돌리기 / 다시 실행 (버튼 / Ctrl+Z, Ctrl+Y), 최근 50단계
- 서비스·영역 설명 툴팁, 스크롤 중에만 보이는 스크롤바
- 서비스 설명 패널: 박스를 선택하면 무엇과 연결하는지·연결하면 안 되는지와 지금 연결 상태(✓ / ⚠) 표시

[스크립트 불러오는 순서]

 5. 알려진 제한 사항
--------------------------------------------------------------
- 박스를 끄는 도중 스크롤하면 중간 상태가 저장될 수 있음 (놓으면 정상 저장)
- 박스를 끄는 도중 Ctrl+휠로 줌하면 박스 위치가 튐
- 저장 데이터에 규칙 위반이 들어 있으면 이후 동작이 거부될 수 있음
- 영역 밖으로 반쯤 걸친 박스가 있으면 좌상단 크기 조절 시 영역이 한 번 튐


--------------------------------------------------------------
 6. 설계 결정 사항  (왜 이렇게 만들었는지)
--------------------------------------------------------------
[처음 명세의 핵심 조건]
- 만들지 않는 것: 세부 설정값 입력(인스턴스 타입, CIDR, IP, 포트, 보안그룹 등),
  실제 AWS 연동, 서버, 로그인/계정, 비용 계산
- 성능 시뮬레이션은 처음 명세에서 "만들지 않는 것"이었으나, 최종 목표에 맞춰 만들기로 바꿨다.
  (2026-10-15 사용자 결정. 7장 [작업 계획 3차] B단계에서 진행)
- 외부 라이브러리 없음, 서버 없음, 데스크톱 브라우저 기준, 한국어 쉬운 안내 문구
- 데이터 구조: nodes(id, type, x, y, parentContainer),
  containers(id, type, x, y, width, height, parentContainer), edges(id, from, to)
- 서비스 데이터: name, category, color, allowedZone, validated
  - allowedZone(배치 위치)와 validated(검증 대상 여부)는 서로 별개 기준
  - validated: false 서비스는 배치·연결만 되고 판정에 영향 없음
- 검증 판정: 오류 규칙 하나라도 위반 → 오류 / 경고만 → 경고 / 모두 통과 → 정상
  - "연결" = 두 박스 사이 직접 연결선, 방향 없음
  - 박스 단위 판정: 규칙 2, 4 / 존재 여부 판정: 규칙 1, 3, 5, 6, 7

[배치·소속]
- 소속 = 박스 중심점을 품는 가장 안쪽 영역.
  영역의 소속은 자기보다 큰 영역만 후보로 본다.
  (그렇지 않으면 AZ 중심점이 자기 안의 서브넷에 걸려 "서브넷 안의 AZ"로 오판)
- 배치·이동·크기 조절은 모두 commit()에서 소속을 다시 계산하고 규칙을 검사한다.
  위반이면 동작 전 상태로 되돌린다. (규칙을 우회하는 경로를 만들지 않기 위함)
- 서비스 박스끼리는 겹칠 수 없다. 겹치면 원래 있던 박스가 우선이다.
- 영역은 포함 관계(VPC > AZ > 서브넷)로 겹치는 것만 허용하고,
  같은 단계 영역끼리는 일부도 겹칠 수 없다.
  (서브넷끼리 반쯤 겹치면 박스 소속이 엉뚱한 쪽으로 바뀌던 버그 때문)
- 겹침 검사는 "이번 동작으로 바뀐 항목"만 대상으로 한다.
  (예전에 저장된 배치에 겹침이 있어도 다른 작업이 막히지 않게)

[VPC 경계선 스냅]
- 대상: IGW, VPC Endpoints, Client VPN.
  박스 중심이 경계선에서 50px(박스 너비 절반) 안이면 붙는다.
- 경계선 위 박스는 "VPC 안, 서브넷 밖" 소속이다. (규칙 2: IGW는 서브넷 밖)
- 스냅한 뒤의 최종 위치로 겹침을 검사한다. 스냅해서 겹치게 되면 거부한다.
- VPC를 옮기거나 크기를 바꾸면 경계선 박스가 따라 움직이고, 캔버스 밖으로 나가지 않는다.

[연결선]
- 연결은 종류와 관계없이 자유롭게 허용하고, 타당성은 검증 단계에서만 판단한다.
- 직각 경로로 그린다.
  fromSide/toSide(연결 변)와 mid(가운데 구간 위치)가 null이면 자동이다.
  자동 경로는 다른 박스를 피해 간다.
- 경로 조절은 "가운데 구간 하나 옮기기"만 한다. (꺾는 점을 자유롭게 편집하는 방식은 복잡해서 제외)
- 겹친 선 벌리기는 그릴 때만 한다. 저장 데이터(fromSide/toSide/mid)는 바꾸지 않는다.
  순서: ① 한 변에 선이 여러 개면 연결점을 12px씩 나눔(상대 박스 쪽 순서, 선이 엇갈리지 않게)
        ② 시작·끝 구간이 다른 선과 같은 줄에서 겹치면 그 끝 연결점을 옆으로 옮김
        ③ 가운데 구간끼리 겹치면 8px씩 옆으로 벌림 (사용자가 옮긴 선은 그대로)
  겹친 선을 그대로 두면 연결하지 않은 박스끼리 이어진 것처럼 보이기 때문이다.
  벌려서 박스를 더 가로지르게 되면 벌리지 않는다.
- 연결선 경로나 연결 변만 바꾸면 검증 결과를 유지한다. (판정에 영향 없음)
- 여러 개를 함께 옮기면 양 끝이 모두 옮겨진 선은 모양(mid)을 유지하고, 한쪽 끝만 옮겨진 선은 자동 경로로 되돌린다 (v1.18).
  한쪽만 옮겨진 선의 예전 경로는 새 위치와 맞지 않아 꼬이기 쉽기 때문이다.

[검증·제안·흐름]
- 구성(박스 위치·소속·연결)이 바뀌면 이전 검증 결과는 지운다.
- 검증 버튼은 켜고 끄는 방식이다: 결과가 있으면 [검증 종료], 없으면 [검증하기] (v1.19).
  흐름 일시 멈춤은 만들지 않는다. 사용자가 원한 것은 "검증을 끝내는 것"이다.
- 개선·제거 제안은 판정(정상/경고/오류)과 별개다. validated: false 서비스도 함께 본다.
[성능 시뮬레이션]
- 계산(js/rules/simulation.js)과 화면(js/ui/simulate.js)을 나눈다. C단계에서 같은 엔진으로 전후 비교하기 위함 (v1.24).
- 요청은 PERF_ROUTES를 따라 사용자에게서 먼 쪽으로만 넘어간다. 같은 종류가 여럿이면 고르게 나눈다 (LB 기본 라운드 로빈).
  사용자는 CloudFront가 있으면 CloudFront로, 없으면 IGW로. EC2는 요청마다 RDS를 한 번 조회.
- 용량은 직접 운영하는 박스(EC2·RDS)만 둔다. LB·IGW는 AWS 문서상 자동 확장·대역폭 제한 없음이라 제한 없음.
  CloudFront도 이 도구에서는 제한 없음으로 본다 (가정).
- 넘친 요청은 실패, 처리한 요청만 다음 박스로. 다음 단계가 정해진 박스(사용자·IGW·LB·EC2)에서 넘길 곳이 없으면 실패,
  마지막 단계(RDS)까지 가야 성공이다 (v1.24.1. 예전엔 RDS 없는 EC2도 성공으로 셈). 응답 시간 = 거친 박스의 기본 지연 × 대기 배수(1/(1-사용률), 90% 이상은 10배).
- 검증 오류가 있으면 실행하지 않는다 (요청이 끝까지 가지 못함). 슬라이더를 끄는 동안은 render() 없이 숫자·막대만 바꾼다.
- 캔버스 표시(v1.25): 박스 색은 카테고리 색 변수(--c, --cbg)를 !important로 덮어써서 바꾼다 (박스는 인라인 변수로 색을 받음).
  트래픽 점은 25요청/초마다 1개(최대 12개, 선 길이 18px마다 1개까지). 도착 박스의 실패 비율만큼 점이 끝 30%에서 빨갛게 사라진다.
  시뮬레이션 탭에서는 검증 흐름 점을 멈추고 트래픽 점만 보여준다 (두 점이 섞이면 헷갈림). 검증 탭으로 돌아가면 다시 돈다.
- 시간 흐름(v1.26): 시뮬레이션 시계가 1초씩 가며 그 순간의 트래픽으로 다시 계산한다 (대기열을 다음 초로 넘기지는 않음).
  탭을 열면 바로 재생. 재생 중 구성을 바꿔도 시계·그래프는 이어진다 (바꾼 전후를 그래프로 비교). 시나리오를 바꾸면 처음부터.
  1초마다 바뀐 것만 고친다 (박스 클래스를 다시 넣으면 깜빡임이 처음부터 시작되고, 점을 다시 만들면 튐).
  그래프는 SVG로 직접 그린다. 응답 시간 눈금은 100ms 단위 올림(최소 200ms).
- 장애·복구(v1.27): 시간은 AWS 기본값을 그대로 쓰고(기다림은 10x 배속으로 줄임), 근거 문서를 패널에 링크한다.
  ALB 상태 확인 기본값(30초 간격, 실패 2번·성공 5번), 모든 대상이 비정상이면 모두에게 보냄(fail open).
  RDS 장애 조치 90초 (문서: 보통 60~120초). Standby가 다른 AZ에 없으면 넘어갈 곳이 없어 계속 실패.
  장애 조치 후에는 Standby가 새 본체로 남고, 원래 RDS가 돌아와도 "예비로 대기" (실제 Multi-AZ와 같음).
  AZ 장애는 그 AZ의 EC2·DB만 멈춘다. LB·IGW는 여러 AZ에 걸친 관리형이라 박스가 어느 AZ에 있든 그대로 동작.
  장애 넣기 모드에서는 박스 끌기·선택·삭제 버튼·크기 조절·Delete 키·되돌리기를 막는다 (실수로 지우지 않게). Esc로 끈다.
  켤 때 선택을 풀어 둔다 (미리 선택한 박스가 Delete로 지워지던 문제, v1.27.1).
  장애 조치 후에는 EC2 → 새 본체(Standby)로 가는 가상의 길을 파란 점선으로 그리고 점이 그 길로 흐른다 (v1.27.2).
  실제로는 DB 엔드포인트(주소)의 DNS가 Standby를 가리키게 바뀌어 앱이 같은 주소로 다시 접속하면 Standby에 바로 연결된다.
  그래서 고장 난 원래 RDS를 거치지 않는다. 점선은 그려진 연결선이 아니라 표시일 뿐이다 (사용자 결정).
  상태 확인 횟수 같은 장애 상태는 시뮬레이션에만 두고 저장·되돌리기 기록에 넣지 않는다.
- 결과 영역 탭 높이는 24px로 맞춘다 (결과 영역이 커지면 캔버스가 줄어 기존 테스트 좌표가 화면 밖으로 밀림).
- 잘한 점은 "규칙 통과"가 아니라 "좋은 구성이 실제로 있을 때"만 보여준다 (v1.23). 박스가 없어서 통과한 규칙은 칭찬하지 않는다.
  규칙마다 praise(ctx)를 두고, 그 규칙에 문제가 하나도 없을 때만 부른다. 판정이 오류여도 잘한 부분은 보여준다.
  기본 연결(판정 3 흐름 연결, 5 앱-DB 연결)과 제거 제안(6·7·10)은 칭찬하지 않는다.
  캔버스 박스에는 표시하지 않는다 (강조·점선·흐름 점이 이미 많음). 목록을 누르면 해당 박스로 이동한다. (사용자 결정)
- 판정·제안 규칙마다 AWS Well-Architected 기준(보안·안정성·성능·비용·운영) 태그와 근거 한 줄을 단다 (v1.14).
  "도구가 그렇다니까"가 아니라 "AWS 기준이 이렇다"로 배우게 하기 위함. 태그를 누르면 해당 기준의 AWS 문서가 열린다.
  기준보다 3-Tier 구조 자체에 관한 규칙(앱-DB 연결, 불필요한 연결)은 "3-Tier 기본"으로 표시한다.
- 설명 문구와 근거는 AWS 공식 문서(docs.aws.amazon.com, aws.amazon.com)만 근거로 쓴다 (v1.15).
  자료가 겹치면 더 최근에 개정된 것, 더 공식에 가까운 것(서비스 사용 설명서, Well-Architected 모범 사례)을 기준으로 한다.
  문서에서 확인하지 못한 내용은 넣지 않는다.
- 흐름 점은 성능 계산이 아니라 검증 결과를 보여주는 표시다.
  (실제 성능 시뮬레이션은 7장 [작업 계획 3차] B단계에서 따로 만든다)
- 검증 후에는 요청 방향(사용자에서 안쪽)으로 한쪽 화살표만 그리고, 점도 그 순서대로 한 구간씩 흐른다 (v1.17).
  판정은 계속 "방향 없는 연결" 기준이다. 화살표 방향은 검증 결과를 보여주는 표시일 뿐이다.
  응답 방향은 그리지 않는다 (점이 왕복하면 초보자에게 헷갈림). 사용자와 이어지지 않은 선은 양쪽 화살표 그대로.
  예외: Route 53·WAF는 경로의 한 단계가 아니라 경로 위 박스가 잠깐 거쳐 가는 곳이다 (v1.21).
    - Route 53: 사용자가 실제로 DNS에 주소를 묻고 답을 받으므로 점 왕복. 돌아온 뒤 CloudFront·IGW로 출발
    - WAF: 따로 오가는 길이 없다 (CloudFront·ALB에 붙은 규칙으로 그 자리에서 검사).
           그래서 점 대신 WAF 박스가 반짝이는 동안 기다렸다가 다음 구간으로 (왕복 표시는 실제와 달라 쓰지 않음, 사용자 결정)
    - 두 선은 양쪽 화살표. 이들을 거쳐 다른 박스로 이어지는 길은 요청 경로로 보지 않는다.
    - 그래서 LB — WAF — CloudFront처럼 WAF를 사이에 두면 CloudFront는 경로 밖이 된다. 이때 제거 제안 10으로 안내 (v1.22)
  방향은 사용자(스마트폰/태블릿/PC/DB 관리자)에서 연결을 따라 자동으로 정한다.
- Auto Scaling은 여러 AZ에 걸치는 관리 그룹이라 박스가 아니라 "그룹 영역"으로 그린다 (v1.12).
  - 덧씌우는 영역(overlay): AZ·서브넷 경계를 넘어 놓을 수 있고, 다른 항목의 소속에는 끼지 않는다.
    (EC2의 소속은 계속 서브넷이다. 그래야 기존 배치·검증 규칙이 그대로 동작한다)
  - 그룹 자신은 VPC에만 소속되고, 영역 전체가 VPC 안에 있어야 한다. 그룹끼리는 겹칠 수 없다.
  - EC2 박스 중심이 그룹 영역 안에 있으면 그 그룹에 속한다. (제안 규칙에서만 사용, 판정에는 영향 없음)
  - 그룹 영역 안쪽은 클릭이 아래 서브넷으로 지나간다. 이름표나 점선 테두리 둘레를 잡아 옮기고, 선택하면 손잡이가 보인다.
    (안쪽 전체를 잡게 하면 아래 EC2·서브넷을 클릭할 수 없어서 제외)
  - VPC를 옮기면 함께 움직이고, AZ를 옮겨도 그대로 있다.
  - 예전 Auto Scaling 박스가 저장 데이터에 있으면 불러올 때 지우고 안내한다. (기본 틀에는 넣지 않음)
- ElastiCache는 RDS 앞의 중계기가 아니다. EC2가 캐시와 DB에 각각 연결한다.

[화면·파일]
- 줌 60~150%. (60% 미만은 격자가 보이지 않음)
- 브라우저 저장소에 배치·줌·스크롤 위치를 자동 저장한다.
- 되돌리기는 render()가 끝날 때 캔버스 상태(nodes/containers/edges)를 비교해 기록한다.
  동작마다 기록 코드를 넣지 않아도 모든 변경이 잡히고, 거부되어 원래대로 돌아간 동작은 상태가 같아 쌓이지 않는다.
  줌·스크롤·선택·검증 결과는 기록하지 않는다. 기록은 저장소에 남기지 않는다(새로고침하면 초기화).
- 파일 분리는 일반 <script> 태그로 한다.
  (ES 모듈은 서버 없이 파일로 열면 브라우저가 막으므로 사용하지 않음)
- 외부 라이브러리 금지는 "사용자 실행 환경"에만 적용한다.
  개발 도구(Node.js, Playwright, ESLint, TypeScript)는 허용하되, 실행 파일에는 넣지 않는다.
- 타입 검사는 기본 강도로 한다. 엄격 모드는 모든 값에 타입을 적어야 해서(경고 600개) 하지 않는다.
  타입 검사가 헷갈려 하는 곳은 동작을 바꾸지 않는 표기(/** @type */, getAttribute)로 맞춘다.

12) [B. 성능 시뮬레이션] 트래픽 부하, 장애, 요청 흐름을 시뮬레이션 — 설계 확정 (2026-10-15)
    - 학습용 모의 실험. 동작 방식은 AWS 공식 문서 근거, 처리량 숫자는 학습용 가정값 (화면에 안내)
    - 결정: 숫자 표시 + 가정값 안내 / 검증 결과 자리에 탭(검증 결과·성능 시뮬레이션) / 재생형(재생·멈춤·배속)
    - 모델: 초당 요청 수 → 지금의 흐름 경로를 따라 분산. 직접 운영 박스(EC2·RDS 등)만 용량 제한,
            관리형(LB·IGW·CloudFront·Route 53)은 자동 확장으로 봄. 사용률 80%↑ 노랑, 100%↑ 빨강(대기·지연·실패)
            지표: 응답 시간, 성공률, 처리량, 박스별 사용률
    - 장애: EC2(LB 상태 확인으로 제외, ASG가 교체) / AZ(그 AZ 전체 정지, RDS는 Standby로 장애 조치)
            DB(Standby 없으면 서비스 중단) / 트래픽 급증·공격(WAF 있을 때만 걸러냄). 박스 클릭으로 끄기 + 시나리오
    - 실행 조건: 검증 오류 없음(경고는 허용). 구성을 바꾸면 멈춤
    - 파일: js/data/performance.js(가정값·근거) / js/rules/simulation.js(계산 엔진, 화면과 분리) / js/ui/simulate.js(패널·그래프·박스 표시)
            C단계에서 Lambda·Fargate 등 성능 정보만 추가해 같은 엔진으로 전후 비교
    - 진행 순서:
      12-1) 엔진 + 트래픽 슬라이더 + 박스 사용률 표시 (정상 상태) — 완료 (v1.24)
      12-2) 시간 흐름 재생 + 캔버스 표현 + 그래프 + 시나리오 — 완료 (v1.25~v1.26)
            - 12-2a 캔버스 (완료, v1.25): 박스 색(사용률별 초록/노랑/빨강, 넘치면 깜빡임, 막대를 박스 안으로 키우고 실패 수 표시)
                           + 트래픽 점(많을수록 촘촘, 넘친·연결 끊긴 박스에서 일부 점이 빨갛게 사라짐)
            - 12-2b 시간 (완료, v1.26): 재생·멈춤·배속(1x/5x) + 최근 60초 응답 시간·성공률 그래프(SVG 직접)
                         + 시나리오 평소(일정)·급증(3배로 뛰었다가 돌아옴)
            - 넣지 않음: 연결선 굵기, 박스별 사용률 그래프, 하루 흐름·점점 증가 시나리오
      12-3) 장애 넣기(EC2·AZ·DB) + 자동 복구(LB 상태 확인, RDS 장애 조치) — 완료 (v1.27)
            결정: 박스·AZ 누르기 + 장애 시나리오 / AWS 문서 시간 + 10x 배속 / 그래프 5분
      12-4) Auto Scaling 동작 — 다음 작업
